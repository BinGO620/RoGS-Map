## 0. 总评与建议

**建议：Reject（现稿）／Major Revision（可救）**。

一句话：**这是一篇诚实、可复现、但"贡献不成立"的稿子。** 三个自报贡献里，第一个是**前作**、第二个作者**自认非新颖**、第三个是**一个 map schema 上的三条观察**；而它最想立住的"重尾承重"结论，**恰好落在已有剪枝文献已知的常识区间**。诚实是优点，但**诚实不构成贡献**——而且本稿的"过度自谦"反而放大了"没有新东西"的第一印象。

## 2. 优点（先说清楚，免得被当成一味贬）

1. **诚实度罕见地高**：主表脚注直书"全模块栈在 5/7 序列上相对 base 劣化"、"第一列是作者前作"、"loop-closure 无可测变化"。多数投稿会藏掉这些，本稿没藏。
2. **同批同码、可复算**：R33 84-run 一次成批，渲染在冻结地图上、固定帧集、臂无关掩码——评测纪律好。
3. **"load-bearing tail" 是一个真·反直觉的实测事实**（clip 重尾 ⇒ 渲染崩），且**不是拍脑袋**，有 tail_census + qerr_probe + L1B 三条链。
4. **负结果被如实登记**（分配/重要度/可见性剪枝全败），对社区有用。

## 3. 重大问题（Major）——按致命度排序

### 3.1 【最致命】全文没有一个外部或朴素基线，R-D 表无法解读
Codec 表（`tab_rd.tex`）只报**自己**的 6×/8.8×/15×，**没有一条对照**：没有 raw-zlib/gzip 基线，没有与压缩文献（HAC 20×、NSVQ 45×；本稿自己引了 `GSZip/HAC`）的任何比较。审稿人无法判断 6× 是"很好"还是"很差"。**离线压缩领域的常识是**：不做基线的压缩表**直接不可评审**。
> 注：本仓 repo 内其实**有**这个基线信息（zlib 把记账字段压到近零；`l1_readout` §5），但**论文正文一个字都没写**——等于把唯一的可比较信息扔了。
> **必须**：加一行 raw-zlib 基线（读 PLY 字节 → gzip），并至少定性对位 HAC/NSVQ 的工作点。

### 3.2 【致命】主表（Table 1）里没有一个是"本文"的结果
Table 1 四列 = `Base (Paper-1 stack)` + `+SWBA` + `+SWBA+LC` + `+SWBA+LC+Gate`。作者自己说：
- 第一列 = **前作**；
- 后三列 = **一个"a wash"的消融**（L361-363）。

⇒ **本稿的旗舰表不含本稿的贡献**。审稿人会问：如果"系统"不是你的、"阶梯"是 wash，那这张表存在的意义是什么？它不代表任何 thesis。
> **必须**：要么把 Table 1 降为附录消融，要么**换一张真正支撑 thesis 的主表**（例如：compression R-D 作主表，storage accounting 作次表）。

### 3.3 【重大】"重尾承重"与已有剪枝文献重叠，且未正面区分
本稿的核心智力内容是"大高斯不是可丢冗余"。但：
- **MGS-SLAM**（本仓自己当作"最像的样本"研究过）**已有"豁免规则"：不透明度 > τ_α 的结构骨架不剪**——这正是"大而承重"的知识。
- **PWAS**（本稿引了）开宗明义："Instead of using opacity heuristics…"，即**按重要性分**正是为治"按幅度剪会崩"。
- 本仓 L1 也早就发现"轨迹不可见剪枝不安全"（同一根因）。

⇒ 审稿人（懂剪枝的）会说：**"大幅度高斯不能按幅度剪"是剪枝文献的常识，不是新发现。** 本稿没有引用/讨论这条脉络，给了读者"首次发现"的错觉。
> **必须**：正文引 MGS-SLAM 的 exemption、PWAS 的 importance 动机、LightGaussian 类，并**明确**把本稿的 delta 收窄为"**SLAM 生长地图的尾部形状 + 范围量化的具体后果**"，而非"发现尾承重"。

### 3.4 【重大】摘要的 "held out at the sequence level" 自相矛盾
摘要（L56-57）："…on seven sequences, **held out at the sequence level**"。但那 7 个 Bonn 序列**就是主面板**，不是 held-out；真正 held-out 的是 codec 的 L3 面板（TUM+Bonn box）。**一句话里把两件事混了**，审稿人会以为系统评测有 held-out，其实没有。
> **必须**：改写为"…on the seven Bonn sequences; the codec additionally reproduces on a held-out panel (TUM + one Bonn sequence)."

### 3.5 【重大】标题的 "Efficient" 与实测 0.456 FPS 冲突
标题（L42）="**Efficient** Dynamic-Scene RGB-GS SLAM"。而效率表：base **0.456 fps**、SWBA 0.354 fps，即**~2-3 秒/帧**。同场对标（本稿自己引的）MGS-SLAM 3 fps、Gaussian-Plus-SDF **150+ fps**。**"Efficient" 是硬伤**：审稿人一眼看到 0.456 fps 配 "Efficient" 标题，会先入为主判"over-claim"。
> **必须**：删 "Efficient"，或换一个不承诺速度的标题（如 *"What a Dynamic-Scene Gaussian Map Costs: System, Compression, and Storage Accounting"*）。

### 3.6 【重大】"贡献一 = 系统"不成立（salami-slicing 风险）
贡献栏第一条是"a complete … system"。但 §3.2 自述系统 = **前作 verbatim**。⇒ 这不是本稿的系统。叠加"作者前作已投 MMM"这一事实，审稿人会提 **salami-slicing / 自引**。本稿虽显式声明继承（好），但**声明了继承，就不能再把"系统"列为本稿贡献**。
> **必须**：贡献栏删"系统"，改为"**a system-level triple report on a prior stack**"（报告，非产物）。

### 3.7 【重大】图太少、太弱——CVM 是"图是灵魂"的会场
全文只有 3 个 includegraphics（图环境 4 个，其中定性对比（**crowd2 单序列单张 PNG**）、R-D 曲线、storage 柱状、**外加 map 侧无一张框图**。且定性图**恰好展示"什么都没有"**（反动态范式下动态物体消失）——对"动态场景论文"是尴尬的主视觉。CVM 的样本（MGS-SLAM 17 页、Gaussian-Plus-SDF）都以多张 GT|render 对比 + 架构图取胜。
> **必须**：至少补 (a) 一张**架构/管线框图**；(b) 2-3 条序列的 GT|render 对比（不只 crowd2）；(c) 一张**重尾分布直方图**（这是本稿唯一反直觉事实，却没有图）。

## 4. 次要问题（Minor）

1. **"empty accounting fields" 的实际收益被夸大**：正文说"fixed fraction … inert"（L226-228），但仓库实测 = **zlib 在熵编码下已把它们压到近零**（`l1_readout` §5）。⇒ 剥离记账字段**几乎不省字节**。正文应写明"inert 但**已被熵编码吃掉**，故不计入压缩增益"，否则读者会以为省 30%。
2. **storage 表报"mean +2.9%"**：符号混合的分布报均值**统计上无意义**、且略带误导。删均值，只报区间 + 各序列。
3. **codec 的绝对 PSNR 很低（~15 dB）**：R-D 表的 PSNR 绝对值（15.37）意味着这些地图**本身渲染质量就不高**。"near-lossless at 6×" 是**在一个低质量基线上**的 near-lossless——正文没承认这个 regime 特殊性。
4. **held-out 面板（TUM）无动态掩码**：L3 只能用全图 PSNR，分区指标不可用。正文说"reproduces the same operating points"，但这是**弱验证**（只看全图）。应明示局限。
5. **bib 有未回源条目**（TC3DGS/MEGA/MEGA `[ID未核]`）被正文当作事实引用。CVM 匿名评审不看 bib 细节，但**一旦被查 = 学术规范问题**。
6. **`\cite{Paper1}` 匿名处理**：bib 里 title 写全了，可能 deanonymize 自引。提交版需处理（"Anonymous submission" 或去掉可识别信息）。
7. **无代价/时间报告**：codec 是离线后处理——**编解码耗时**没报。工程论文该报。
8. **§5 "What the map is made of" 与 §4 "What a Dynamic-Scene Map Is Made Of" 标题几乎重复**，且 codec 与该节内容**有交叠**（都讲 rot3/iso-scale）——结构可再收。

## 5. 结构性问题（决定"能不能救"）

本稿现在**同时**承载：系统 + 跟踪 + 渲染 + 效率 + 分区协议 + codec + R-D + 泛化 + 存储账 + 重尾 + 消融。**14 页里每样都浅**。这是典型的 **"broad but shallow"**——审稿人会说"没有一条深到能立住"。

**唯一可能立住的深点 = "地图侧刻画"**（存储账 + 重尾）。建议**重排**：
- 主线 = "动态场景 GS-SLAM 的地图是什么、能压多小、代价是什么"；
- 系统/跟踪/渲染/效率 = **背景，一段带过**（不作贡献）；
- 分区协议 = 仪器（现已如此）；
- **新增 raw-zlib 基线 + 重尾直方图 + 多序列定性图**。

这样贡献从"三件浅的"收敛成"**一件有骨头的**"，反而更可能过。

## 7. 正面结论（诚实收口）

这篇稿子**不是"没东西"**——它有系统、有同批证据、有能跑的 codec、有一条反直觉的实测事实、有罕见的诚实。它的问题是**"把三件浅的东西并列当成三个贡献，而没有把唯一深的东西做深"**。按 §5 重排 + §6 P0 五条，它可以变成一篇**CVM 收得下的"地图侧系统+刻画"论文**（CVM 收过 MGS-SLAM 的剪枝启发式、收过 150+fps 的制度性短文）。**但它现在这个样子，会被以"no clear contribution / no baselines"拒。**
